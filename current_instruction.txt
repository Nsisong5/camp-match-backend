CHUNK 2 — Domain Layer

Objective: The pure business concepts Identity is built around — no FastAPI, no SQLAlchemy, no database, nothing except the shared kernel.
Files to modify: domain/value_objects.py, domain/entities.py, domain/events.py.
value_objects.py — two value objects:
EmailAddress — wraps a single email string. On construction: strip surrounding whitespace, lowercase the whole address, and check it has a basic valid shape (something in the form local-part@domain, domain contains at least one dot) using only the standard library (re is fine — do not add email-validator or any third-party package here; that check happens separately at the API boundary). Reject anything longer than 254 characters. An invalid value raises ValueError at construction — the application layer is responsible for turning that into the right application-level error (see Chunk 5). Two EmailAddress instances are equal if their normalized values match.
AccountStatus — an enum with exactly three members: ACTIVE, SUSPENDED, DISABLED. Nothing else. (No PENDING_VERIFICATION — see ADR-018.)
entities.py — one entity, UserAccount:
Fields: id (reuse the shared-kernel EntityId directly — do not invent a competing identifier type, per the handoff's own instruction; you may alias it as IdentityId = EntityId for readability within this module), email (EmailAddress), password_hash (str — this is the already-hashed, opaque output of the password hasher; the raw password never reaches this class, ever), status (AccountStatus), created_at (datetime).
Behavior the entity itself should expose (as methods, not free functions elsewhere):
A way to construct a brand-new account in the ACTIVE state (this is what RegisterAccount will call).
A way to transition to SUSPENDED/DISABLED/back to ACTIVE that enforces the state machine — reactivating an already-active account or disabling an already-disabled one should be a harmless no-op at the entity level, not an error (the use case layer decides whether to treat that as noteworthy; the entity itself just doesn't do redundant work or throw over it).
A read-only way to check "is this account allowed to authenticate right now" (true only when status == ACTIVE) — AuthenticateUser will call this rather than comparing the enum itself, so the rule lives in exactly one place.
events.py — three domain events, each a frozen dataclass extending the shared-kernel DomainEvent (which already supplies event_id and occurred_at): UserRegistered (carries the new account's id and email), AccountDisabled (carries the account id), AccountReactivated (carries the account id). No UserAuthenticated event — see ADR-022.
Business rules to enforce here, not later: identifier stability (an EntityId, once assigned, never changes for the life of the account — nothing in this class should ever let it be reassigned); raw passwords never touch this file in any form.
Dependencies you may use: shared-kernel EntityId, shared-kernel DomainEvent, Python stdlib (dataclasses, enum, re, datetime). Nothing else.
Tests you must write: tests/unit/identity/domain/test_email_address.py (valid addresses normalize correctly and compare equal regardless of case/whitespace; malformed addresses raise ValueError; a 255+ character address is rejected) and tests/unit/identity/domain/test_user_account.py (a new account starts ACTIVE; disabling then reactivating produces ACTIVE again; disabling twice doesn't error; can_authenticate is only true when ACTIVE).
