CHUNK 2.1 — IDs

Objective: One identifier value object, used everywhere an entity needs an ID.
Architectural context: ADR-006 — plain UUID4, wrapped so it's a real value object (equality, hashing, string conversion) rather than a bare uuid.UUID scattered through the codebase.
Files to create:
src/camp_match/shared_kernel/domain/identifiers.py
Implementation instructions:

from __future__ import annotations
from dataclasses import dataclass
from uuid import UUID, uuid4

@dataclass(frozen=True, slots=True)
class EntityId:
    value: UUID

    @classmethod
    def new(cls) -> "EntityId":
        return cls(uuid4())

    @classmethod
    def from_string(cls, raw: str) -> "EntityId":
        return cls(UUID(raw))

    def __str__(self) -> str:
        return str(self.value)
        
Individual modules (once built) may alias this for readability, e.g. UserId = EntityId, or wrap it in a thin subtype — that decision belongs to whichever module needs it, not to the shared kernel.
Dependencies you may use: Python stdlib uuid, dataclasses. Nothing else.
You must not: add a database-facing TypeDecorator here — that belongs in platform/db/ and arrives in Phase 3, since the shared kernel domain layer must not know SQLAlchemy exists.
Tests you must write: tests/unit/shared_kernel/test_identifiers.py — EntityId.new() produces unique values; two EntityIds wrapping the same UUID are equal and hash equal; from_string round-trips with str(); an invalid string raises ValueError.
Acceptance criteria: new tests pass; mypy src/camp_match/shared_kernel/domain/identifiers.py is clean.


CHUNK 2.2 — Errors

Objective: The two-tier error hierarchy from ADR-007 — domain errors (business rule violations) and application errors (use-case failures that map to specific HTTP statuses).
Files to create:

Implementation instructions:
domain/errors.py — pure business-rule violations, no HTTP concept anywhere near this file:

class DomainError(Exception):
    """Base class for violations of a business rule. Framework-agnostic."""

class InvariantViolationError(DomainError):
    """Raised when an entity or aggregate would be left in an invalid state."""
    
application/errors.py — use-case-level failures, each maps to exactly one HTTP status (the mapping itself lives in Phase 3+/per-module error handlers, not here):

class ApplicationError(Exception):
    """Base class for use-case-level failures."""

class NotFoundError(ApplicationError):
    """The requested resource does not exist."""

class ValidationError(ApplicationError):
    """Input failed validation beyond what the DTO layer already checked."""

class ConflictError(ApplicationError):
    """The requested operation conflicts with current state (e.g. duplicate, already booked)."""

class UnauthorizedError(ApplicationError):
    """The caller is not authenticated."""

class ForbiddenError(ApplicationError):
    """The caller is authenticated but not permitted to perform this action."""
                                                                                                                                                                                                                                                                                                                                                                            
Business rules: DomainError subclasses are raised from shared_kernel/domain and per-module domain/ code only. ApplicationError subclasses are raised from application/use_cases/ code only. Adapters (including API routers) never raise either directly — they let them propagate and get translated by the error-handler layer (extended in Chunk 2.6/Phase 3 and per-module later).
You must not: give these classes an HTTP status code attribute directly — that mapping is an adapter-layer concern (API rules, Chunk 08_API_RULES.md), not a property of the error itself. Keep the domain/application layers HTTP-agnostic.
Tests you must write: tests/unit/shared_kernel/test_errors.py — each subclass is instantiable, carries a message, and isinstance checks confirm the hierarchy (e.g. NotFoundError is an ApplicationError but not a DomainError).
Acceptance criteria: new tests pass; no import of fastapi anywhere in either new file (confirm manually — the automated check arrives in Chunk 2.6).
