CHUNK 5 — Use Cases

Objective: The actual business logic, implementing the inbound ports from Chunk 4, built entirely against outbound ports (repository, hasher, session, clock, event bus) — no real database, no real JWT library, no FastAPI anywhere in this chunk. You should be able to fully test everything here using fake/in-memory implementations of the outbound ports.
Files to create: one file per use case under application/use_cases/ — register_account.py, authenticate_user.py, refresh_session.py, logout.py, get_identity.py, disable_account.py, reactivate_account.py. Each is a class implementing the matching inbound port, constructed with whichever outbound ports it actually needs (not all of them need all five — GetIdentityById needs only the repository, for instance).
A governing rule for this whole chunk, stated once: format-level validation (is this a plausible email shape, is the password within the allowed length) is Pydantic's job at the API boundary (Chunk 9) — do not duplicate that here. What belongs in this chunk is validation Pydantic structurally cannot express: uniqueness, state transitions, "does this credential actually match this account." Two sources of truth for the same rule is worse than one correct source.
RegisterAccount — steps, in order:
Construct an EmailAddress from the raw input (letting ValueError surface as InvalidAuthenticationRequest if it somehow reaches this layer malformed).
Ask the repository for an existing account with that email. If one exists, log at INFO ("registration_rejected_duplicate", with the attempted email) and raise IdentityAlreadyExists.
Hash the raw password via PasswordHasher.hash.
Construct a new UserAccount (new EntityId, the normalized email, the hash, ACTIVE), using Clock.now() for its created_at.
Persist it via the repository's add, inside a UnitOfWork — commit on success.
Race-condition handling: even after step 2's check, two near-simultaneous registrations for the same email can both pass that check before either commits. If the repository's add fails because the database's own unique constraint rejects it (see Chunk 6), catch that specific failure here (or let the repository translate it — your call, document which in the Completion Report) and raise IdentityAlreadyExists, exactly as if step 2 had caught it. The database is the real guarantee; step 2 is just a fast, friendly first check.
Build and publish a UserRegistered event via the shared-kernel event bus, with occurred_at from the same Clock.
Log at INFO: "registration_succeeded", with the new identity's id and email.
Return the response DTO — id, email, status, created_at. Never anything password-related.
AuthenticateUser — steps, in order (read this one carefully — the ordering is a deliberate security property, not arbitrary):
Normalize the input email.
Look the account up by email.
If no account was found: log at WARNING ("login_failed", reason "account_not_found", the attempted email — this is a server-side-only log, never returned to the caller) and raise InvalidCredentials. Stop here.
If an account was found, verify the password via PasswordHasher.verify. If it fails: log at WARNING ("login_failed", reason "invalid_password", the account's id — not the email, not the password) and raise InvalidCredentials. Stop here.
Steps 3 and 4 must raise the exact same exception to the caller. This is the anti-enumeration rule from the handoff (Part 11) — an attacker probing for valid emails must not be able to tell "no such account" apart from "wrong password" from the API response alone. The log, which the caller never sees, is allowed and expected to be specific — that's what "observable without leaking secrets" (Part 34) actually means here, and it's exactly the debugging detail you asked to keep.
Only now, with credentials confirmed correct, check the account's status. If it can't authenticate (per the entity's own check from Chunk 2): log at WARNING ("login_blocked", the specific status, the account id) and raise AccountSuspended or AccountDisabled accordingly — this response is allowed to be specific, since the caller has already proven they hold valid credentials for this exact account.
Call AuthenticationSessionPort.issue_tokens for the account's id.
Log at INFO: "login_succeeded", the account id.
Return the token pair.
RefreshSession — steps: call AuthenticationSessionPort.refresh with the incoming token, and return whatever it returns. All the actual validation (does this token exist, is it expired, is it already revoked) lives inside the session adapter itself (Chunk 7), since it owns the refresh-token storage — this use case is a thin pass-through on purpose, so the rotation mechanics have exactly one owner. Log at INFO on success ("refresh_succeeded") — the adapter is responsible for its own WARNING-level logging on the failure paths, since it's the one that knows why a token was rejected (not found vs. expired vs. already used).
Logout — steps: call AuthenticationSessionPort.revoke with the incoming token. This must succeed (204-equivalent, no exception) whether the token was actively valid, already revoked, or not recognized at all — logout is idempotent by design (see Chunk 7 for why: the caller who's trying to log out shouldn't get an error just because they clicked twice). Log at INFO either way, noting whether it revoked something real or was a no-op.
GetIdentityById — steps: parse the input id into an EntityId, look it up, raise IdentityNotFound if absent, otherwise return the response DTO.
DisableAccount / ReactivateAccount — steps (mirror each other): look the account up (raise IdentityNotFound if absent — this one legitimately can happen, since nothing guarantees the id passed in refers to a real account), call the entity's own transition method from Chunk 2, persist via update, publish the matching event (AccountDisabled/AccountReactivated), log at INFO with the account id and new status, return the response DTO. If the account was already in the target state, this is a harmless no-op (per Chunk 2's entity behavior) — still log it, still return success, just don't publish a duplicate event for a transition that didn't actually happen (check the status before and after to decide whether to publish).
Dependencies you may use: the ports from Chunk 4, the domain types from Chunk 2, the errors from Chunk 3, shared-kernel Clock/EventBus/UnitOfWork, structlog for the logging calls described above. Nothing from fastapi or sqlalchemy.
Tests you must write: for each use case, build a minimal in-memory fake for whatever outbound ports it needs (a dict-backed fake repository, a fake hasher that just does a trivial reversible transform, a fake session port that returns predictable tokens) and place these fakes under tests/support/identity_fakes.py so all seven use-case test files can share them. Cover, at minimum: registration success and duplicate-email rejection; authentication success, unknown-email failure, wrong-password failure (assert both produce the identical exception type), suspended-account failure, disabled-account failure; refresh success and logout idempotency (calling logout twice doesn't raise the second time); get-by-id success and not-found; disable/reactivate success and the no-op-when-already-in-that-state case
